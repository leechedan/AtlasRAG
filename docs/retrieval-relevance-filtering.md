# 检索结果相关性过滤：问题讨论与方案

日期：2026-08-27

## 背景

当前语料规模不大。观察到的现象：查询即使与语料库中任何文档都不相关，
`/search/text` 仍然会返回 `top_k` 个结果——因为检索链路本质是"矿场里挖出
最像的 k 块矿石"，不是"矿石里有没有金子"的判断器。文档量小时这个问题被
放大：候选池本身就小，随便一个查询也能在池子里凑出"矮子里拔将军"的
`top_k`。

检索结果目前主要消费方是下游 LLM/Agent 做 RAG 生成回答，不相关结果混入
上下文会稀释真正相关的内容、增加 token 成本、并可能诱导模型引用不相关
内容作答。

## 检索链路现状

`app/api/routes/search.py` → `search_text_hybrid` / `search_images`
（`app/store/qdrant_client.py`）：

- 文本：`BAAI/bge-m3` 一次编码产出 dense（1024维）+ sparse（类 SPLADE）
  两路向量，加上第三路"原文逐字包含查询词"的全文匹配 `Prefetch`（详见
  `docs/proper-noun-retrieval-quality.md`），Qdrant 用 **RRF
  （Reciprocal Rank Fusion）** 融合三路排序，返回固定 `top_k` 个结果，
  不做任何分数过滤。
- 图片：`search_images` 没有融合，是纯 CLIP cosine 相似度，同样直接返回
  `top_k` 个结果，不做分数过滤。

## 阈值过滤（对分数设 cutoff）的具体缺点

文本和图片两条链路的分数性质完全不同，需要分开讨论。

### 文本链路（RRF 融合分数）——阈值过滤基本不可行

1. **RRF 分数不是相似度，是排名的函数**：`score = Σ 1/(k_rrf + rank_i)`
   （Qdrant 默认 `k_rrf=60`），只取决于一个文档在各路 prefetch 里排第
   几名，跟它和查询"到底有多像"没有直接关系。两个语义上八竿子打不着的
   `(query, doc)` 对，只要 doc 在某一路里恰好排第 1，分数就可能和真正
   强相关的命中差不多高。
2. **无法跨查询/跨语料标定统一阈值**：分数上界由参与融合的路数和每路的
   `limit` 决定，是结构性的，不是查询难度或相关度的函数。今天调出来的
   "能用"的某个阈值，语料多了几个文档、或者换一批查询，分布就会漂移，
   阈值需要不断重新标定。
3. **小语料场景恰好是最容易失效的场景**：候选池小时，"最不差"的候选很
   容易在某一路里拿到较高排名（哪怕整体不相关），RRF 分数因此"虚高"，
   阈值反而拦不住想拦截的假阳性——这正是当前观察到的现象的根源，不是
   阈值没调对，是这个分数种类天生不适合做绝对判断。
4. **第三路全文子串匹配会进一步扭曲分数**：一个词逐字命中会让该路排名
   骤升，抬高融合分数，但"逐字命中一个词"和"整体语义相关"是两回事，容
   易把分数进一步和"真相关"脱钩。

### 图片链路（CLIP cosine 相似度）——阈值理论可行，但仍有已知坑

1. cosine 相似度是真实的向量夹角度量，语义上比 RRF 分数更可解释，可以
   设阈值。
2. 但预训练视觉-语言模型的 embedding 空间存在各向异性（anisotropy）——
   毫不相关的图文对 cosine 相似度也常年漂浮在一个不低的基线上（不是从
   0 开始的），"多高算相关"需要用具体模型
   （`OFA-Sys/chinese-clip-vit-base-patch16`）在自己语料上跑一批已知
   相关/不相关的 pair 统计出经验阈值，不能拍脑袋定一个数，而且这个基线
   会随领域（图表/实拍/文档扫描件）漂移。

### 核心结论

"设个阈值过滤掉低分"这个直觉方案，在当前文本链路上几乎不成立（分数种
类不对），在图片链路上勉强成立但需要额外的经验标定和持续维护成本。

## 候选方案

围绕"文本链路的分数种类不适合做绝对判断"这个核心结论，候选方案本质上
是三类思路：换一个语义上可判断的分数、不做硬判断把信号透传给下游、用
相对/统计特征代替绝对阈值。

### 方案 A：引入 cross-encoder reranker，在 rerank 分数上做阈值

对 RRF 融合后的 top-N（比如 20~30）候选，用 `BAAI/bge-reranker-v2-m3`
做一次 `(query, chunk)` 精确打分，替换/补充融合分数。

- **优点**：reranker 输出的是针对具体 `(query, doc)` pair 的相关度打
  分，不依赖候选池里还有谁、排第几——语义上比 RRF 分数干净得多，理论上
  支持设一个相对稳定的阈值（甚至可以过 sigmoid 转成类概率值）。副作用
  是顺带解决了 `docs/proper-noun-retrieval-quality.md` 里点名但没做的
  短板 #1（无 reranker，排序精度本身也会提升）。
- **缺点**：多一次模型前向推理，有延迟代价；即使分数种类变好了，阈值
  依然需要在自己的语料上标定（不是免费午餐，只是标定难度从"结构性不可
  行"降到"经验调参"）；模型和依赖已经在计划内（`FlagEmbedding`），落地
  成本可控。

### 方案 B：不做硬过滤，暴露原始信号，交给下游 LLM/Agent 判断

`/search/text` 除了融合分数外，把每个 hit 命中了哪几路（dense/sparse/
exact-match）、以及可选的原始 dense cosine 相似度一起返回；不相关时不
由检索服务下判断，由调用方（RAG 生成层）结合这些信号 + 实际 chunk 内容
自己决定要不要采纳、要不要回答"不知道"。

- **优点**：零额外模型开销；不需要标定全局阈值这种脆弱的事——LLM 看内
  容本身判断相关性，比任何分数都可靠；给的是能力而不是决策，不锁死"要
  不要硬拒绝"这个还没想清楚的问题。
- **缺点**：把复杂度转移到了下游 prompt 设计上，且如果下游是别的
  Agent/团队维护，这个约定需要跨服务对齐；不能减少无关 chunk 占用的
  token（信号只是辅助判断，不减少召回数量本身）。

### 方案 C：相对阈值 / 分数差距检测（score-gap），不设绝对 cutoff

不比较绝对分数，而是看 top-k 内部的分数分布——比如"是否存在一个显著的
分数断层（第 1 名比第 2 名高出一大截，后面又趋于平缓）"，或者"是否所有
候选分数都挤在一个很窄的区间里（说明没有谁显著更相关，大概率是全不相
关）"，用相对特征而不是绝对数值做判断。

- **优点**：不依赖分数的绝对语义，理论上对 RRF 分数的"结构性不可标定"
  问题免疫，因为看的是相对形状而不是绝对高度；小语料场景下"全都差不多
  低"这个模式本身就是判断依据。
- **缺点**：启发式规则本身也需要调参（断层多大算显著），可解释性不如
  A/B；候选数量很少时（比如 `top_k=3`）统计意义不足，规则容易失效；据
  目前调研没有成熟的通用实现可以直接套用，属于定制启发式。

## 推荐：A + B 组合，暂不单独做 C

A 解决的是"分数种类不对"这个根因——只要分数种类是干净的（reranker 分
数），后面无论是服务端设阈值还是把分数透传给下游做判断，都变得可行了；
B 是低成本的补充，把 A 算出来的干净分数连同命中路径信号一起透传，让"是
否要硬拒绝"这个决策先不做死。C 单独作为主方案性价比不高——启发式规则的
维护成本不比标定一个 reranker 阈值低，而且 A 上线后 C 想解决的问题（分
数不可比）已经不存在了，除非未来 A 也不够用了再考虑叠加。

图片链路：如果需要过滤，可以用同样思路的简化版——不引入新模型，而是在
自己的语料上跑一批经验样本，把 CLIP cosine 相似度的"不相关基线"标定出
来，作为可选的软阈值透传给下游，而不是在接口层硬过滤。

## 附录：现有架构里 API 与 Worker 为什么各自常驻一份模型

方案 A 讨论 reranker 部署位置时提到"只需要挂在 API 进程"，这里详细说明
现有 BGE-M3（dense+sparse）、Chinese-CLIP 为什么在 API 和 Worker 两个进
程里各自加载了一份，而不是共用一份——这是理解 reranker 该放哪里的前提。

**两者是两个独立的操作系统进程，进程内缓存天然不能跨进程共享**：
`docker-compose.yml` 里 `api` 和 `worker` 是两个独立 service/容器，用同
一个 `Dockerfile` 构建，但跑不同的启动命令（`uvicorn app.api.main:app`
vs `python -m app.worker`），各自单独申请一块 GPU device reservation。
`app/models/embeddings.py::get_text_embedder()` /
`app/models/clip_model.py::get_clip_embedder()` 用的 `@lru_cache(maxsize=1)`
是 Python 解释器进程内的缓存，作用域到进程为止——两个独立进程各自有自己
的 Python 解释器和内存空间，`@lru_cache` 缓存不可能跨进程共享。想要"整
个系统只加载一份模型"，唯一办法是额外引入一层进程间通信（比如把
embedding 单独拆成一个模型推理服务，API 和 worker 都通过网络调用它），
但目前系统里没有这一层，两边各自直接 `from_pretrained()` 加载。

**为什么一开始要拆成两个独立进程，而不是都放进 API 进程里跑**：
- **API 进程**跑的是同步的请求/响应路径（`/search/text`、
  `/search/image`）：查询文本/图片要在处理这次 HTTP 请求的过程中实时
  embed，延迟直接体现为用户等待时间，必须在处理请求的同一进程里同步
  跑完，不能排队等别的进程处理。
- **Worker 进程**跑的是异步的摄取任务（`app/jobs/tasks.py` 里经 RQ
  入队的 `ingest_file_job`/`ingest_directory_job` 等）：文档解析、
  embedding、写入 Qdrant 这些工作可能耗时很长（`docs/QA.md` Q4：单文
  件 `job_timeout=3600` 秒，目录批量导入 `job_timeout=-1` 无限超时）。
  如果把这些工作放进 API 进程同步跑，会让处理摄取请求的那个 HTTP 连接
  长时间挂起、和其他并发请求抢占同一个进程的资源，还拿不到 RQ 现成的
  排队/重试/超时/状态查询能力（`docs/QA.md` Q5 里 `job_id` 竞态问题的
  修复，正是建立在"摄取是独立 RQ job"这个前提上的）。拆成独立进程消费
  队列，就是为了让"摄取"这种慢、非交互式的工作不拖累"检索"这种快、交
  互式的工作，两者可以独立扩缩容、独立失败恢复。

**两边各自都需要跑一次 embedding 推理**（API 端是"查询时 embed 查询文
本/图片"，worker 端是"摄取时 embed 文档chunk/图片内容"），而两边是不同
进程，所以只能各自在自己的进程里独立构造并常驻一份模型——这不是设计疏
漏，是"进程隔离"这个决策的直接代价：换来的是 API 的响应延迟不会被摄取
任务拖慢，摄取任务本身的超时或崩溃也不会拖垮检索服务。

**代价**：同一份模型权重在两个进程里各占一份显存/内存。`docs/QA.md`
Q11 提到的 `HF_HOME` 共享磁盘缓存解决的是"重复下载"（两边从同一份磁盘
缓存加载权重文件，不用各自下载一遍），但运行时两个进程各自把权重实例
化进自己的显存，这部分占用磁盘缓存共享解决不了，是两份。

这个代价在这个项目里**已经被最初的架构设计明确核算过、判断为可接受**，
不是后来才发现的隐患：`docs/superpowers/specs/2026-08-25-multimodal-
retrieval-service-design.md` 第 2 节"组件划分理由"原文写的是——部署环境
是 NVIDIA DGX Spark（128GB 统一内存），"API、Worker 各自常驻加载一份模
型到 GPU；DGX Spark 121GB 统一内存下两份模型（GB 级别）无压力，v1 不必
为省显存再拆独立推理微服务"。也就是说双份模型常驻这个选择本身是拿"更
简单的部署拓扑"换"闲置内存"，在当前单机、统一内存足够大的部署形态下
是净收益为正的取舍，而不是没考虑过的疏漏。

如果未来显存吃紧（比如换到显存更小的机器，或者语料/流量增长到需要更
大的模型），可选的解法是把 embedding（以及将来可能的 reranker）单独拆
成一个独立的模型推理服务进程，API 和 worker 都通过网络调用它而不是各
自 `from_pretrained()`，这样权重在系统里只真正加载一次；但这会新增一
层服务，以及相应的网络延迟、可用性依赖（这个服务挂了两边都不能用）等
新问题，按最初设计文档的判断和目前语料/流量规模，还没到必须做的地步。

**这对 reranker 放哪里的启发**：reranker 只在检索路径用（对 RRF top-N
候选重排），不参与摄取写入，按照"谁需要在自己的同步路径里跑推理，谁就
在自己的进程里常驻模型"这个现有原则，reranker 只需要挂在 API 进程，不
需要像 BGE-M3/CLIP 那样在 worker 进程里也加载一份——这是 reranker 相比
现有两个模型更轻的一点。

## 实施状态

方案 A 的排序部分（RRF 粗筛 top-N 候选池 + cross-encoder 精排，两阶段
架构）已按 `docs/superpowers/specs/2026-08-27-two-stage-rerank-design.md`
实施：`/search/text` 默认走两阶段 rerank（`reranker_enabled=False` 可关
闭回退到单阶段 RRF）。方案 B（透传命中路径信号）以及"完全不相关时接口
具体该返回什么（空列表 vs 带信号继续返回）"仍未实施/未决定，留待后续按
需求优先级排期。
