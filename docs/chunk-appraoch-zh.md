# Markdown 分片方法全景：按方法说明适用场景

除了上一条讲的"标题递归切分"，常见的还有下面几类，各有取舍：

## 1. 固定长度切分（Fixed-size / Character Splitting）
按固定字符数或 token 数硬切，通常带一点 overlap。

- **适用场景**：非结构化纯文本、日志、聊天记录这类没有明显层级的内容；或者作为兜底方案处理没有标题的段落。
- **不适用**：公司章程、流程文档——会切断条款和表格，丢上下文。

## 2. 递归字符切分（Recursive Character Splitting）
按分隔符优先级递归切（先按段落 `\n\n`，切不动再按句子，再按词），是目前最通用的默认方案。

- **适用场景**：通用文档、博客、说明书类正文，结构不强但有自然段落。
- **在 OA 文档里的用法**：通常作为标题切分之后的"二次切分"手段（就是我上条示例里的做法），单独用于章程/流程文档效果一般。

## 3. 标题层级切分（Markdown Header-based Splitting）
按 `#`/`##`/`###` 结构切，metadata 自动带层级路径。

- **适用场景**：结构清晰的规章制度、Wiki、技术文档、公司章程、SOP 流程文档——**这是你这类文档的首选基础方法**。
- **局限**：如果某个 section 特别长（比如财务流程一整章几千字），还得配合二次切分。

## 4. 语义切分（Semantic Chunking）
不看格式，用 embedding 计算相邻句子/段落的语义相似度，相似度骤降的地方切开。

- **适用场景**：段落之间话题切换频繁但没有明确标题标记的长文本，比如会议纪要、访谈记录、非结构化制度说明。
- **在 OA 场景**：适合处理"一段话里混了多个知识点"的老旧文档（很多公司历史制度文件格式混乱，没规范用标题分级），可以用语义切分做兜底补救。
- **代价**：需要额外调用 embedding 模型做切分，成本和延迟比规则切分高，且对中文长句语义边界判断不如英文稳定。

## 5. 结构感知切分 / 元素级切分（Structure-aware / Element-based Splitting）
识别 Markdown 里的元素类型（表格、代码块、列表、引用块），每种元素按各自规则处理，保证原子性。

- **适用场景**：**报销流程、财务流程这类图文表混排的文档**——报销标准表、审批矩阵表必须整体保留，不能被字符切分打断。
- 实现上通常是"结构切分打底 + 表格/代码块单独识别保护"的组合，而不是单独存在的方法。

## 6. 父子分层切分（Parent-Document / Hierarchical Chunking）
切两层：小 chunk 用于向量检索匹配，大 chunk（父节点，如整条/整章）用于最终喂给 LLM。

- **适用场景**：**公司章程**这种"条款短但引用密集"的文档——小片段提高检索精度，父级片段保证回答时上下文完整，是你这类法律条文类文档的推荐搭配方式，而不是单独替代方案。

## 7. 滑动窗口 + 句子重叠（Sliding Window with Sentence Overlap）
本质是固定长度切分的改良版，重叠单位从字符改成完整句子，避免语义断在句子中间。

- **适用场景**：连续叙述性强、上下文强依赖前后句的内容，比如流程说明里"承接上一步"的过渡描述。
- 常作为其他方法（标题切分/结构切分）内部的补充规则，而非独立方案。

## 8. Agentic / LLM 驱动切分
让 LLM 直接阅读文档，自己判断"在哪里切合适"，输出带语义标签的 chunk。

- **适用场景**：文档结构极不规范、人工整理成本太高、且对准确率要求高的场景（比如把扫描件 OCR 出来的老旧财务制度重新结构化）。
- **代价**：成本最高，通常只用于一次性清洗历史文档，不用于实时/批量场景。

## 小结：你的三类文档该怎么组合

| 文档 | 主方法 | 辅助方法 |
|---|---|---|
| 公司章程 | 标题层级切分（按"条"） | + 父子分层切分（小chunk检索/大chunk回答） |
| 报销流程 | 标题层级切分 | + 结构感知切分（保护表格/步骤列表） |
| 财务流程 | 标题层级切分 | + 结构感知切分（保护表格）+ 句子级重叠 |

三类都不建议单独用固定长度切分或纯语义切分做主方案——前者破坏结构，后者对中文制度类文本的边界判断不够稳，成本也更高。语义切分适合留给你未来遇到的"历史遗留、格式混乱"的老文档做兜底清洗。
